# 通用工程规范

## 一、修改前先理解现有代码

* 修改代码前，先阅读相关源文件，理解现有实现。
* 明确受影响的组件、函数、类型和数据流。
* 优先复用项目中已有的组件、工具函数、依赖和实现模式。
* 不要在未检查的情况下，假设某个文件、接口、依赖或配置一定存在。

## 二、优先进行小范围修改

* 优先采用能够直接解决问题的最小改动。
* 修改局部逻辑时，不要无必要地重写整个文件。
* 不要顺带进行无关重构、公共 API 重命名或业务逻辑变更。
* 除非用户明确要求，否则应尽量保持现有功能和行为不变。

## 三、保持项目代码风格一致

* 遵循项目已有的命名规范、格式规范、目录结构和架构约定。
* 优先沿用相邻代码的实现方式，不要随意引入新的编码模式。
* 如果已有能力可以满足需求，不要新增依赖。

## 四、正确处理不确定性

* 先检查代码和配置，再作出判断。
* 如果需求存在歧义，且会影响架构或业务行为，应先提出有针对性的澄清问题。
* 明确区分已经确认的事实与基于现有信息作出的推断。

## 五、验证代码修改

* 根据项目实际情况，运行相关测试、类型检查、代码检查或构建命令。
* 如果无法执行某项检查，应说明原因。
* 只有实际执行并成功通过的检查，才能报告为通过。
* 不要声称执行过实际上没有运行的命令。

## 六、说明修改结果

完成修改后，应说明：

1. 修改了什么，以及修改原因。
2. 涉及哪些文件。
3. 实际执行了哪些验证，以及验证结果。
4. 是否仍存在风险或需要后续处理的问题。
